Overview diagram

One diagram showing how the settings depend on each other: The backend you choose decides which quality options below actually take effect.

Two things to take from the diagram: A higher API number doesn’t mean better quality; first and foremost it decides which runtime, wrapper and graphics driver the commands go through. Ephinea’s advanced anti-aliasing is available from D3D9 up; D3D11/12 also use dgVoodoo and Vulkan uses DXVK; only dgVoodoo Model is strictly limited to the D3D11/12 paths.

Rendering backend (D3D / Vulkan)

PSOBB’s engine natively only issues Direct3D 8 commands. The launcher options don’t rewrite models, textures or scene lighting; they decide which compatibility layer, output API and graphics driver those commands pass through afterwards. Strictly speaking, the dropdown mixes native APIs, translation paths and wrapper output backends, rather than being a set of equal “renderers”.

First, get the rendering chain right

A modern backend doesn’t turn PSOBB into a native D3D11 or D3D12 game. The game still produces the same D3D8-era vertices, textures, fixed-function state and draw calls; the compatibility layer rewrites them into resources, state and shaders a later API understands, then hands them to the graphics driver.

PSOBB content and logic
    ↓  D3D8 commands
Ephinea compatibility/enhancement layer (D3D9 path, AA, AF, post-processing)
    ├─ D3D9 ───────────────────────────────→ D3D9 driver
    ├─ D3D9 → Microsoft D3D9On12 ─────────→ D3D12 driver
    ├─ D3D9 → dgVoodoo ─→ D3D11 or D3D12 → matching driver
    └─ D3D9 → DXVK ───────────────────────→ Vulkan driver

This also explains why the launcher’s custom files are dgVoodoo_d3d9.dll or dxvk_d3d9.dll: the wrapper receives the D3D9 calls Ephinea outputs and passes them on to D3D11, D3D12 or Vulkan. Ephinea’s official Launcher 3.5.0 release notes also give these two file names and their versions.

Quality: why it’s usually the same, but not guaranteed pixel for pixel

An API doesn’t provide “D3D12-grade quality” by itself. Character polygon counts, texture resolution, materials, lighting formulas, shadows and effects are still decided by PSOBB. With identical output resolution, AA, AF, SSAO and shaders, D3D9, D3D11, D3D12 and Vulkan should produce very similar images.

But the paths aren’t bit-exact replays. Wrappers have to emulate the D3D8/9 fixed-function pipeline and convert legacy formats and state into modern shaders and resources; these details can cause visible differences:

  • Sampling and filtering: texture coordinate precision, mipmap LOD, anisotropic filtering and half-pixel rules can make textures slightly sharper or softer.
  • Depth and blending: differences in depth buffer formats, comparison precision and Alpha Test/Blend emulation can show up as seams, flicker or wrong transparency ordering.
  • Fixed-function emulation: vertex fog, lighting, reflections and texture stages have to become shaders; wrapper bugs cause missing fog, wrong reflections or inconsistent colours.
  • Colour and presentation: gamma, colour space, scaling filters and how the swap chain is composed affect brightness, contrast or final sharpness.

So when backends show obvious black blocks, wrong fog, missing reflections or an overall darker image, treat it as a compatibility difference or translation bug, not as an API’s normal “look”. The main value of switching backends is finding the most correct and stable implementation for your GPU, driver and window mode.

Why aren’t D3D9on12 and D3D12 the same thing?

Both end up calling the D3D12 driver, but the translator, the device model exposed above and presentation management all differ. “It ends up using D3D12” isn’t enough to judge how they behave.

What’s actually different between D3D11 and D3D12?

The short answer: both share dgVoodoo’s D3D9 front end, state translation and fixed-function emulation, and only diverge in the final layer of resource management, command submission, synchronization and presentation. So their features and expected quality are the same; D3D12 isn’t an enhanced-quality D3D11.

dgVoodoo author’s official notes also don’t treat D3D12 as an unconditional upgrade: its automatic selection doesn’t default to D3D12 on x86/x64, and they record opposite compatibility results on specific NVIDIA and AMD drivers. So the more professional way to choose is to go by correct rendering and stable frame times, not by the API number.

The simplest order to choose in:try Direct3D 11 (2.87.1) first; if the image and running are fine, there’s no need to switch. On AMD, if you see known D3D11 driver symptoms such as solid-colour polygons, try D3D12 of the same version, and turn off Radeon Anti-Lag if it crashes. On NVIDIA, don’t make dgVoodoo D3D12 your first troubleshooting path; keep D3D11 and then try an older dgVoodoo, D3D9 or Vulkan, changing only one variable at a time.

How D3D12 and Vulkan relate underneath

D3D12 and Vulkan belong to the same generation of low-level graphics APIs, and their design ideas are very close. Both hand the application or translation layer much of the work the D3D11 driver used to do implicitly: recording GPU commands ahead of time, declaring resource states explicitly, organizing pipeline objects, binding descriptors and handling CPU/GPU synchronization. In the PSOBB setups on this page, that work is done not by the game but by dgVoodoo or DXVK.

The table above is an approximate mapping of responsibilities, not a one-to-one match of handles, lifetimes or synchronization semantics. For example, a D3D12 fence is an incrementing timeline object closest to a Vulkan timeline semaphore; a traditional Vulkan fence mainly tells the host one submission has finished, and binary semaphores are often used for dependencies between queues.

Their main difference isn’t “high or low level” but ecosystem and interface conventions: D3D12 belongs to Microsoft’s Windows/Xbox graphics stack, with DXGI, HLSL/DXIL and the Windows driver model; Vulkan is defined by Khronos, runs across Windows, Linux and Android, usually uses SPIR-V, and has its own presentation and extension system. Vulkan tends to expose more explicit choices, but both require the layer above to manage resource lifetimes, synchronization and pipelines correctly.

PSOBB → D3D8 → Ephinea D3D9 → dgVoodoo → D3D12 → Windows graphics driver → GPU
PSOBB → D3D8 → Ephinea D3D9 → DXVK     → Vulkan → Vulkan graphics driver  → GPU

So you can think of dgVoodoo + D3D12 and DXVK + Vulkan as two similar modern low-level translation routes, but they aren’t equivalent. The two translators emulate D3D9 fixed function, shaders, old texture formats, depth buffers, swap chains and device loss differently; these implementation differences decide PSOBB’s correctness, stutter and stability far more than the API name. For a 30 FPS old game, low-level APIs’ theoretical throughput advantage usually doesn’t matter; prefer the path that renders correctly and stably.

Device Lost errors: which backends get them, and which avoid them?

This error means the client got a device-lost event and then failed to recover (Reset failed). It isn’t a “dgVoodoo 2.79.3 error” or a “D3D12 error”. When troubleshooting, first tell apart two kinds of cause:

  • Traditional D3D8/9 device loss: triggered by exclusive fullscreen losing focus, Alt-Tab, the UAC secure desktop, a lock screen, a screensaver or a display mode change; this is the most common cause of this error in PSOBB.
  • Real GPU/driver resets: Windows TDR, driver crashes, unstable overclocks, overlay/injection conflicts or translator bugs. D3D12 can show up as Device Removed/Hung and Vulkan as VK_ERROR_DEVICE_LOST; no backend is guaranteed to be immune.

An early Ephinea update already advised clearly: to avoid traditional Device Lost from UAC, lock screens, screensavers and similar, use dgVoodoo D3D11/12, not D3D9On12. But dgVoodoo’s current official notes also strongly warn of D3D12 GPU hangs on NVIDIA, so “avoids traditional Device Lost” doesn’t mean “the most stable backend on every GPU”. DXVK’s default behaviour can be checked in its official configuration notes.

Troubleshooting order when you hit this error: if you were on D3D8, D3D9 or D3D9On12 and had just Alt-Tabbed, seen a UAC prompt, locked the screen or changed display mode, it’s the known traditional device loss; switch to D3D11 2.87.1. If you were already on dgVoodoo D3D11/12 or Vulkan, it’s no longer normal focus-loss behaviour: check Reliability Monitor or Windows Error Reporting for LiveKernelEvent 117/141, and the system log for display driver events (commonly Display 4101), then check your graphics driver, overclocks and overlays. On NVIDIA, retest D3D11 2.87.1 first; on AMD, if solid-colour textures appear only on D3D11, then test D3D12 2.87.1 under controlled conditions.

What each backend means

Direct3D 8

The game’s original rendering. Calls the system’s D3D8 directly with no translation layer; closest to the original 2003 behaviour.

  • ✅ The fewest variables; good for confirming the game itself runs properly
  • ⚠ On Win10/11 with high refresh rates and multiple monitors, prone to crashes, tearing and black screens after Alt-Tab
  • ⚠ Lacks the full advanced AA set of the D3D9-and-up paths; legacy Device Lost behaviour remains

Direct3D 9

A lightweight wrapper turns D3D8 calls into D3D9. Tiny overhead, behaviour close to the original, slightly more stable than pure D3D8.

  • ✅ Broadly compatible; almost every card that supports D3D9 can run it
  • ✅ Supports Ephinea’s advanced AA options such as SSAA, SMAA, MSAA and HSAA
  • ⚠ Still depends on the quality of the system’s D3D9 driver
  • ⚠ The official changelog notes MSAA/HSAA may break some reflections on the D3D9 path; switch to SMAA or SSAA if you hit problems

Direct3D 9on12

Microsoft’s official D3D9-on-D3D12 translation layer. D3D8 calls go through D3D9 first, then Windows’ built-in d3d9on12.dll translates them to D3D12 for the graphics card.

  • ✅ Lets the system map D3D9 workloads onto D3D12; mainly a platform compatibility path
  • ⚠ It keeps the behaviour of Ephinea’s D3D9 front end and isn’t dgVoodoo’s D3D12 mode
  • ⚠ Ephinea’s official testing notes it can still hit Device Lost after UAC, the secure desktop or a lock screen; not recommended as a first choice on ordinary PCs

Direct3D 11 (2.79.3 / 2.87.1)

Uses dgVoodoo2 to take Ephinea’s D3D9 calls and output them to D3D11. Legacy fixed-function state is emulated by the wrapper as modern GPU resources and shaders.

  • ✅ Avoids native D3D8/9 Device Lost problems; windowed mode, Alt-Tab and modern desktop composition are usually more reliable
  • ✅ You can choose between presentation models such as Auto, Discard and Flip
  • 📌 Try first by default: broad hardware coverage, and a sensible starting point for troubleshooting against D3D12
  • 📌 2.79.3 is the older stable version, 2.87.1 the newer one, more complete but occasionally with new bugs

Direct3D 12 (2.79.3 / 2.87.1)

As above, but dgVoodoo2 outputs to the more modern D3D12.

  • ✅ May lower CPU/driver overhead on some newer graphics card and driver combinations
  • 📌 Quality won’t be higher than D3D11, and PSOBB usually shows no obvious frame rate gain
  • 📌 Always presents with Flip Discard; the other “dgVoodoo Model” choices can’t turn it into the traditional BitBlt model
  • ⚠ dgVoodoo’s official notes currently warn clearly of D3D12 GPU hangs on NVIDIA drivers; not recommended as the first choice on NVIDIA
  • ⚠ On AMD, try D3D12 if D3D11 shows solid-colour polygons; if it crashes, turn off Radeon Anti-Lag and retest

Vulkan (2.3.1 / 2.7.1)

Uses DXVK Translates Ephinea’s D3D9 calls to Vulkan. It takes a different driver compilation, resource management and presentation path, useful for checking whether a problem exists only in the Direct3D driver stack.

  • ✅ On some hardware, can improve stutter or display errors specific to the D3D path
  • ⚠ Brief stutters may occur the first time Vulkan shaders/pipelines are created; how bad depends on the driver and DXVK version
  • ⚠ DXVK doesn’t officially support Windows; screen recorders, overlays, RTSS and other injection software may also conflict with it
  • 📌 2.3.1 is the older stable version, 2.7.1 is the newer version

Direct3D 11 / 12 / Vulkan (Custom)

Uses Your own custom dgVoodoo or DXVK version. Per Ephinea’s official convention, place an x86 dxdg folder in the game directory with an x86 dgVoodoo_d3d9.dll or x32 dxvk_d3d9.dll.

  • You have to download and place the right version of the files yourself; for advanced users testing newer translation layers
  • Placing the wrong files causes a black screen or crash at launch

Anti-aliasing

Aliasing isn’t a single phenomenon. In PSOBB you’ll see at least three kinds: geometric aliasing on polygon edges, texture and alpha-test aliasing where distant fine textures and fences shimmer as the camera moves, and general undersampling from rendering at a low resolution and scaling up. Different AA algorithms target different things, so you can’t just compare the 2x/4x after the name.

Which layer implements AA?

Ephinea’s AA isn’t a quality feature that D3D11, D3D12 or Vulkan hands out automatically. The client implements it when creating render targets and processing the final image: MSAA changes the render target’s multisampling parameters; SSAA raises the internal render size and scales down; SMAA runs spatial post-processing after the scene is done. The Ephinea developers’ explanation confirms this order too.

Basic algorithms

  • None — anti-aliasing off. Best performance, sharpest edges, but jagged.
  • MSAA 2x / 4x — Multi-Sample AA. Computes triangle coverage and depth/stencil results at several positions within a pixel, usually sharing one pixel shading result. It mainly smooths geometric outlines and is cheaper than SSAA, but it can’t fix shimmering inside textures or shader aliasing, and often does nothing for leaf/fence edges made by alpha testing. Microsoft’s MSAA rasterization rules also state clearly that it doesn’t remove surface aliasing.
  • SSAA 2x / 4x — Super-Sample AA. Ephinea renders the width and height each 2 or 4 times larger, then scales back to the output resolution with linear filtering. It improves geometric edges, texture detail and some transparent edges together, the most complete effect, but greatly increases pixel shading, video memory and bandwidth cost.
  • SMAA Low / Medium / High / Ultra — Subpixel Morphological AA. After the scene is finished, it searches colour/brightness edges for shapes and blends neighbouring pixels. Effective on geometric edges and some alpha-test edges at relatively low cost, but with no extra geometric or temporal samples it can’t truly recover sub-pixel detail or reliably remove texture shimmer as the camera moves. Higher quality widens the search and precision; the side effect is that fine text, the HUD or textures may look slightly soft.
  • HSAA 2x / 4x — Hybrid-Sampling AA. In Ephinea this means SSAA at a given factor + MSAA at the same factor, not a cheap compromise between the two. It raises both the internal resolution and the coverage samples per pixel; the quality ceiling is high, but it is also one of the heaviest options.

How big are the SSAA / HSAA factors really?

The factor applies both horizontally and vertically. With an output size of W × H, SSAA Nx renders at (N·W) × (N·H), which is N² times the pixels. Don’t mistake SSAA 4x for rendering only 4 times the pixels.

Even though PSOBB is old, 4K output with 4x may fail to start, drop frames or exhaust the VRAM the wrapper is configured with.

Why was 20-year-old hardware smooth, yet an RTX 4090 / 5090 can struggle at 4K max settings?

The two claims don’t contradict each other. Original PSOBB’s geometric complexity, shader complexity and 30 FPS cap are all low, and cards from 20 years ago met the design target at 640×480, 800×600 or 1024×768 without modern post-processing. The modern launcher lets you multiply the pixels, samples and full-screen passes per frame by several orders of magnitude; the game content is still old, but the work the GPU actually does is no longer a 2004 workload.

Estimating memory and sample counts at 4K max settings

4K output is 3840×2160, about 8.29 million pixels. With SSAA 4x the internal size becomes 15360×8640, about 132.7 million pixels. A single RGBA8 colour buffer takes about 531 MB and a 32-bit depth buffer another 531 MB; before counting resolve targets, Bloom/SSAO/DoF intermediate textures, wrapper caches and game textures, these two alone exceed 1 GB.

Add HSAA 4x and the colour and depth targets must hold about 4 times the multisample data, so these two buffers alone could theoretically approach 4.25 GB. Each frame also shades about 132.7 million pixels and processes about 530.8 million coverage/depth samples, then resolves, scales down to 4K and runs several post-processing passes. This load is mainly limited by fill rate, memory bandwidth, cache and the wrapper’s implementation, and has little to do with how many triangles the models have.

How should you think about the RTX 4090 and RTX 5090?

The RTX 4090 has 24 GB of GDDR6X; the RTX 5090 goes up to 32 GB of GDDR7. NVIDIA’s official specs list memory bandwidth of about 1008 GB/s and 1792 GB/s. So in bandwidth- and memory-heavy loads such as SSAA/HSAA and multiple full-screen passes, the 5090 usually has more headroom. See the official NVIDIA 5090 vs 4090 spec comparison.

But this doesn’t mean the 5090 raises PSOBB frame rates in proportion to bandwidth. Ephinea is an old 32-bit program going through D3D8→D3D9→dgVoodoo/DXVK state translation; the bottleneck may be single-threaded CPU, synchronization, the driver, internal wrapper limits or allocating huge render targets. A 4090 at 4K + SSAA/HSAA 4x + SSAO High + several shaders may hit full load, drop below 30 FPS or crash when resource allocation fails; the 5090 is usually more comfortable, but isn’t guaranteed to make every extreme combination sensible either.

In practice: smooth old hardware shows it can carry the “original scene load”; a top card struggling shows the player has created hundreds of times the pixels, more samples and more full-screen passes. When judging performance, record the full combination rather than just saying “it’s a 20-year-old game” or only comparing D3D11 and D3D12.

Combinations (X + SMAA)

SMAA sits in the post-processing stage after the scene is finished, so it can keep working on high-contrast edges that remain after MSAA, SSAA or HSAA resolve/downsampling:

  • MSAA + SMAA — MSAA provides real geometric coverage samples and SMAA cleans up the remaining identifiable edges. Usually a well-balanced quality/cost combination.
  • SSAA + SMAA — SSAA first suppresses high-frequency detail and sub-pixel aliasing, then SMAA handles the remaining edges. High quality, but SMAA can’t offset SSAA’s huge pixel cost.
  • HSAA + SMAA — SSAA, MSAA and SMAA stacked together; an extreme option, not an everyday “compromise”.

Anisotropic filtering

AF fixes textures blurring at oblique angles, not jagged model outlines. When a floor, wall or road stretches into the distance, the area of texture one screen pixel covers becomes a long strip rather than a square. Ordinary bilinear/trilinear filtering uses a roughly square sample footprint, tends to pick too low a mipmap and loses distant detail; AF adds samples along the long axis so textures on slopes stay sharper.

  • 2x / 4x:Improves oblique sharpness on floors and walls at lower cost; good for old GPUs or integrated graphics.
  • 8x:Usually covers nearly all the visible benefit; a good general setting.
  • 16x:Maximizes sharpness of oblique textures; on modern discrete cards the extra cost is usually small, but it still adds texture sampling and bandwidth load.

Why does AF sometimes make things shimmer more?

AF keeps more high-frequency texture detail. If original or modded textures lack proper mipmaps or contain heavy sharpening or fine lines, the sharper distance can also bring shimmer, moiré and visual noise. That isn’t necessarily a bug in AF: first drop 16x to 8x/4x, or use textures with proper mipmaps; SSAA can suppress this aliasing further.

Recommendation: with original textures and a modern GPU, start at AF 16x ; if distant areas shimmer badly after installing custom HD textures, drop to 8x/4x and check the texture pack’s mipmaps. AF doesn’t remove jagged character outlines; you still need suitable AA.

dgVoodoo Model (swap chain mode)

This setting only concerns the dgVoodoo path. It controls the DXGI swap chain’s Present model, i.e. how the finished back buffer is handed to the Windows desktop compositor or the display. It affects latency, window compatibility, Alt-Tab and capture, and doesn’t change the scene’s sampling quality.

Important limitation: these modes are mainly for D3D11 output. According to dgVoodoo’s official notes, D3D12 output must use Flip Discard; even if the launcher still offers other choices, D3D12 can’t fall back to the traditional BitBlt swap chain.

  • Auto — chosen automatically by dgVoodoo based on the backend and window mode; the default recommendation.
  • Discard — the traditional BitBlt model, which discards the old frame when showing a new one. Best compatibility on Win 7 / old drivers, but can’t use Win10+ DWM optimizations.
  • Sequential — the traditional BitBlt model, but keeping previous frames. Rarely used.
  • Flip Discard — the modern Flip model + discarded buffer contents. Cuts unnecessary desktop copies and allows modern presentation optimizations; actual latency still depends on V-Sync, window mode, the driver queue and DWM scheduling.
  • Flip Sequential — the Flip model, but keeping old frames. Slightly more overhead than Flip Discard.

Recommendation:

  • For D3D11, Auto is fine in most cases; test the others one by one only if capture, Alt-Tab or window composition misbehaves
  • If screen recorders can’t capture D3D11 after switching to Flip, change back to Discard
  • If D3D12 has presentation or capture problems, changing Model usually won’t help; switch to D3D11 + Auto/Discard

Ambient occlusion

SSAO (Screen-Space Ambient Occlusion) is a screen-space approximation of contact occlusion. It reconstructs the spatial relationship of nearby surfaces from the current frame’s depth buffer (implementations may also use normals), and adds low-frequency darkening where light struggles to reach, such as corners, object seams and under characters’ feet.

It isn’t dynamic shadows or global illumination. Real shadows need to know the relationship between the light, the occluder and the surface being shadowed; SSAO only knows the limited depth information the camera currently sees, so it can only give the visual cue that objects feel more grounded and solid.

  • Disabled — off. Closest to the original look, best performance.
  • Low — suits low resolutions or limited hardware; sampling noise, banding or edge changes may be more visible.
  • Medium — a good balance of contact feel and cost; a sensible starting point for ordinary players.
  • High — higher sampling/processing quality; shadows are usually steadier and finer, but cost rises sharply with output resolution.

Limits advanced players should know

  • Screen-edge leaks: when the sample area goes off screen there’s no scene data, so occlusion may suddenly fade or vanish.
  • Incomplete occlusion information: objects off camera or completely hidden behind the foreground aren’t in the current depth buffer and can’t contribute correct occlusion.
  • Halos at depth discontinuities: large depth jumps where foreground meets background can form unnatural dark or light edges.
  • Transparency and particles: transparent objects, effects and the HUD often don’t write depth like ordinary solids, so they may be left out or wrongly covered.
  • Relation to AA: SSAO/DoF need to read or resolve multisampled depth/colour buffers correctly. Ephinea’s 2022-09-06 update specifically fixed their combination with MSAA/HSAA, so if an old client has problems, update fully first.

Recommendation: Start with Medium Watch characters’ feet, corners and screen edges; move up to High if there are no halos, noise or frame drops. Choose Disabled.

Extra (additional features)

These are experience switches Ephinea adds on top of the original, quality-of-life toggles unrelated to visual quality; green = on, grey = off.

  • FAST STARTUP — skips the SEGA / Sonic Team / SOFTDEC logo animations at startup and goes straight to the login screen.
  • CLEAN CAPTURE — makes the game’s built-in screenshots read a “clean” image from the scene render target, so later overlays such as Lua Addons aren’t included. It isn’t a switch for better recording quality; whether third-party recorders can capture still depends on the backend and swap chain.
  • MOTION BLUR — motion blur. Blends samples along the direction of motion or accumulates neighbouring frames to imitate motion trails during a shutter exposure. It makes low-frame-rate motion look more continuous, at the cost of detail and text legibility while moving; at PSOBB’s fixed 30 FPS the trails are especially noticeable, so turn it off if you value motion clarity or are prone to motion sickness.
  • RARE DROP SFX — rare drop sound. Plays an extra sound when a rare item drops, so you’re less likely to miss it while farming.
  • BANK SHORTCUTS — bank shortcut keys. When on, you can store/take items and turn pages quickly with the keyboard in the bank, a big efficiency gain.
  • LARGE BANK WINDOW — larger bank window. Shows more items at once and cuts down on page turning.

Screenshot compatibility: Ephinea’s developers state clearly that Clean Capture won’t include Addons, and D3D12’s built-in screenshots can’t capture Addons either. If you must capture add-on UI too, try D3D8/9 with Clean Capture off first, or a compatible Flip presentation mode under D3D11; you can also just use the system’s or OBS’s window capture.

Shaders

These are screen-space post-processing effects based on the final colour, depth or edge information; green = on, grey = off. They add no model or texture detail but reinterpret pixels that were already rendered. Stacking several effects stacks their costs and artefacts too, and the final look also depends on the order they run in.

  • BLOOM — bloom. A typical implementation extracts brighter pixels, blurs a lower-resolution brightness image several times and adds it back to the original. It imitates the feeling of strong light spreading in a lens or the eye and creates no new lighting. Too strong, and white HUD elements, technique effects and bright textures bleed into each other, looking overexposed or hazy.
  • DEPTH OF FIELD — depth of field. Estimates each pixel’s distance from the focal plane from the depth buffer (the Circle of Confusion) and blurs out-of-focus areas. PSOBB’s transparent effects, character names and HUD don’t necessarily have depth consistent with solid geometry, so edges may get halos, the foreground may pick up background colour, or text may blur.
  • CEL SHADING — cel shading. Strengthens outlines with brightness/depth/normal edge detection and may compress continuous shading, pushing forms towards a cel-animation look. It’s screen-space stylization, not a remake of character materials; small textures and high-contrast HUD elements may also be treated as outlines.
  • TONEMAPPING — tone mapping. Uses a non-linear curve to remap internal brightness to the display range, changing shadow compression, highlight roll-off, contrast and saturation. PSOBB isn’t a modern HDR renderer, so here it’s better understood as reshaping display tone and colour response, not generating HDR dynamic range out of nothing.

Stacking effects and troubleshooting

  • One at a time: pick a stable backend and AA first, then turn on one shader at a time. Only then can you tell which one causes crashes, blurring, frame drops or colour problems.
  • Bloom + Tonemapping:If tone mapping lifts highlights or contrast, it changes the bright areas Bloom extracts; the combined result isn’t simply the sum of the two effects.
  • DoF / SSAO + MSAA:Both depend on depth resolve. Keep the client updated; if outline halos appear, lower AO and turn off DoF first, then change AA.
  • Several full-screen passes: post-processing usually runs per output pixel, and 4K has 4 times the pixels of 1080p. One cheap effect doesn’t mean several together are still cheap.
  • Vulkan / Wine:Shader compilation, depth formats and injected overlays make combinations more complex. If you hit crashes, turn all shaders off first, and bring them back once the backend is confirmed stable.

Original look and clarity first: all four off.Light modernization: turn on Tonemapping alone first, then add Bloom to taste.Anime style: turn on Cel Shading alone and check whether the outlines are clean.Screenshot atmosphere: try DoF + Bloom, but they aren’t recommended long-term when you need to spot enemies and drops at a distance.

FAQ

Q: The game shows a black screen or crashes after switching. What now?
A: Reopen the launcher and switch back to a conservative option such as Direct3D 9 or Direct3D 11 (2.79.3) . Settings only affect rendering and won’t damage character data.

Q: Why are there two sets of version numbers (2.79.3 / 2.87.1)?
A: Different dgVoodoo / DXVK versions have different fixes and regressions. The older one is kept as a fallback and the newer one is for trying out. If you hit a bug in the newer version, you can switch back to the older one for now.

Q: I changed options but the frame rate didn’t change?
A: PSOBB’s native frame rate cap is 30 FPS, and the translation layer can’t break the game’s internal frame lock. Switching backends is mainly for stability and Compatibility, not higher frame rates.

Q: It still crashes, and it’s not about rendering?
A: See About crashes and check system-level settings such as DEP, compatibility, UAC and antivirus exclusions.

Q: Why doesn’t anti-aliasing take effect / make any difference?
A: Advanced AA is implemented by the Ephinea client in the render target and post-processing stages, not provided automatically by dgVoodoo / DXVK. The full advanced options are available from D3D9 up; D3D8 isn’t suited as an advanced AA path. MSAA only handles geometric coverage edges, so texture interiors still shimmer; try SSAA to improve that, or SMAA if you just want cheap smoothing.

Q: D3D9on12 already uses D3D12, so why pick D3D12?
A: D3D9on12 is Microsoft’s system compatibility layer that maps D3D9 commands onto D3D12, keeping the D3D9 device model on top; the launcher’s D3D12 has dgVoodoo take over D3D9 emulation, resource management and Flip presentation. They only share the final driver API; the translators and compatibility behaviour are completely different. To avoid traditional Device Lost, prefer dgVoodoo D3D11; consider D3D12 only when there are specific D3D11 texture glitches on AMD.

Q: Can D3D12 be thought of as Microsoft’s Vulkan?
A: As an introductory analogy, yes: both are modern low-level APIs that explicitly manage commands, resource state, descriptors, pipelines and synchronization. But they aren’t the same API or wrappers of each other; D3D12 belongs to the Windows/Xbox ecosystem and Vulkan is a cross-platform standard. For PSOBB it’s more accurate to say dgVoodoo translates D3D9 to D3D12 and DXVK translates the same kind of workload to Vulkan.

Q: The image got blurry / the colours changed after turning on Shaders?
A: That’s the nature of post-processing, not a bug. The most common culprits are BLOOM (blur) and TONEMAPPING (deeper, more saturated colours). Turn them off one by one to find the one you don’t like.

Q: How are CLEAN CAPTURE and dgVoodoo Model = Discard related?
A: Both relate to whether recording / streaming can capture the image properly. Turn on CLEAN CAPTURE first; if OBS still can’t capture under D3D11, switch Model from a Flip type back to Discard. D3D12 always uses Flip Discard, so switch to D3D11 before testing Model.
